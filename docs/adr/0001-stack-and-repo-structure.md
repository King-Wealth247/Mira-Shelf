# ADR-0001: Technology stack and monorepo structure

- **Status:** Accepted
- **Date:** 2026-11-10
- **Deciders:** Project team
- **Related:** Spec Sections 0 (stack), 12 (project structure); Stage 0 of IMPLEMENTATION_PLAN.md

## Context

The *Cahier des Charges* v1.0 fixes the technology stack and recommends a single repository with
clearly separated frontend, server-side, database and operations areas. Server-side and database
code must never be bundled into the mobile app.

## Decision

Adopt a **monorepo** with the Section 12 layout: `app/` (React Native CLI, TypeScript, Android
first), `supabase/` (migrations, tests, Edge Functions), `services/companion/` (EC2 service),
`scripts/` (operator tools + manifest), `deploy/`, `e2e/`, `docs/`, `.github/workflows/`.

The stack is fixed and non-negotiable: React Native + Supabase (Postgres/Auth/RLS/Storage/Edge
Functions) + existing AI integration behind a provider-independent adapter + AWS EC2.

## Consequences

- Clear separation keeps secrets and server code out of the shipped app.
- The native `android/`/`ios/` projects are generated by the RN CLI on a dev machine (not scaffolded
  into Git as a bootstrap) — see `app/README.md`.
- CI runs lint, type-check, unit/component, migrations+pgTAP, secret scan, dependency audit, APK build.

## Alternatives considered

- **Polyrepo** — rejected: harder to keep shared Zod schemas and types in sync, more release overhead
  for a 1–3 person team.
- **Expo-managed RN** — not assumed (A-01); if the project turns out Expo-managed, every native module
  in Section 17 must be re-verified.
